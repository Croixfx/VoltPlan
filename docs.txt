1. WHAT VOLTPLAN DOES
---------------------
VoltPlan is a Flutter app (Android, iOS, web, desktop) with a FastAPI backend.
It takes an architectural floor plan and produces an electrical design for it:

  1. Create a project (client, building type, location, standard).
  2. Upload the plan (PDF, PNG or JPG, up to 25 MB).
  3. Calibrate the scale: tap two points on the plan and enter the real
     distance between them.
  4. AI analysis: a vision model reads rooms, doors, windows and fixtures.
  5. A canonical geometry model is built (walls, openings, obstacles,
     coordinates in millimetres).
  6. A rules engine (RS IEC 60364) proposes electrical points: lights,
     switches, sockets, appliances, smoke detectors, fans, outdoor lights,
     data and TV outlets, emergency lighting.
  7. A circuit engine groups points into circuits, sizes cable and breakers,
     and assigns phases L1/L2/L3.
  8. A BOQ engine builds the bill of quantities; a cost service prices it in
     Rwandan Francs (materials, labour, contingency).
  9. The app shows all of it: interactive plan canvas with IEC symbols,
     circuit schedule, BOQ, cost estimate and a report screen.

Principle: the AI only observes the drawing. Every electrical decision comes
from deterministic, traceable rules. Each point records the rule that placed
it, the geometry it used and whether it is "proposed" or "needs confirmation".


2. ARCHITECTURE
---------------
Flutter app (lib/)
  app/            theme and routes
  core/           API client, endpoints, shared widgets
  features/       dashboard, projects, floor_plan (upload, scale calibration),
                  analysis, electrical (recommendations, canvas, circuits),
                  boq, cost_estimate, reports, settings
  shared/         models (project, room, electrical_point, circuit, ...),
                  AppState (single ChangeNotifier), mock_data
  Talks to the backend at http://127.0.0.1:8000/api (api_endpoints.dart).

Backend (backend/app/)
  api/routes/     health, projects, uploads, analysis, scale, equipment
  services/       vision_service        AI providers (gemini, openai, mock)
                  canonical_geometry_service / coordinate_transform
                  geometry_engine       OpenCV wall snapping, door swings
                  electrical_engine     turns rules into traceable points
                  circuit_engine        circuits, phases, wiring arcs
                  boq_engine / cost_service
                  scale_service         scale calibration maths
                  plan_analysis_service pipeline orchestrator
  engineering_rules/  RS IEC 60364 rules (base class allows other standards)
  catalog/        equipment catalog (single source of truth, see section 3)
  models, schemas, db   SQLAlchemy (SQLite by default), Pydantic

Pipeline order (plan_analysis_service.py):
  vision -> canonical geometry -> electrical points -> circuits -> BOQ -> cost

4. HONEST STATE OF THE PROJECT
------------------------------
Works and tested:
  - Full backend pipeline end to end, driven by the mock vision provider.
  - Scale calibration (API and UI), equipment catalog, circuits, BOQ, cost.
  - Flutter screens for the whole workflow.

Not yet proven:
  - Real-world accuracy. The mock provider returns the same six rooms for any
    upload. The Gemini and OpenAI providers exist but have not been validated
    against real plans, so output quality on actual drawings is unknown.
  - The app has not been run end to end against the live backend in this
    session (only unit, widget and API tests).

Known weaknesses:
  1. Geometry is inferred from AI bounding boxes, so rooms are rectangles.
     L-shaped rooms, thick or curved walls and multi-storey plans are not
     handled. Wall detection by OpenCV is used for snapping, not as the
     source of room shapes.
  2. Scale needs a known dimension on the drawing. Nothing reads dimensions or
     scale bars automatically.
  3. There is no manual editing. Users cannot add, move or delete equipment,
     or fix room boundaries and door positions, before generating circuits.
  4. Safety-relevant placement (wet zones, door-swing clearance) depends on
     what the AI detected. A missed shower or door is not caught.
  5. New-equipment prices and placement quantities (e.g. 2 data outlets per
     office) are reasonable defaults, not verified against suppliers or the
     standard text. Review them with a qualified engineer.
  6. Only RS IEC 60364 rules exist. BS 7671 and NEC appear in the settings
     screen but have no rule implementation.
  7. Sample drawings and offline projects still use local mock data in the
     Flutter app (mock_data.dart), and they skip calibration.
  8. Repository hygiene: AI_PROVIDER defaults to "mock"; no CI; no
     .gitattributes (LF/CRLF warnings on every commit); app-icon PNG changes
     are still uncommitted; build/, uploads and the zip in the repo root
     should not live there.
  9. No authentication or multi-user support; the output is advisory and must
     be reviewed and signed off by a licensed engineer.


5. HOW TO RUN IT
----------------
Backend:
  cd backend
  python -m venv venv ; .\venv\Scripts\activate   (Windows)
  pip install -r requirements.txt
  copy .env.example .env      (set AI_PROVIDER and the matching API key)
  python -m uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
  API docs: http://localhost:8000/docs
  Tests: python -m pytest -q

AI provider settings (backend/.env):
  AI_PROVIDER=mock | gemini | openai
  GEMINI_API_KEY / OPENAI_API_KEY as needed. With a real provider and no key,
  analysis now fails with a clear message instead of using mock data.

Flutter:
  flutter pub get
  flutter run -d chrome        (or -d windows, or a connected device)
  flutter analyze ; flutter test
  On a phone/emulator, change ApiEndpoints.baseUrl from 127.0.0.1 to the
  machine's address.


6. HOW TO PROCEED (RECOMMENDED ORDER)
-------------------------------------
Step 1 - Prove it on real plans (highest priority)
  - Set AI_PROVIDER=gemini or openai with a real key and run 10-20 genuine
    floor plans of varying quality through the app.
  - Record what the AI gets wrong (room boundaries, doors, wet fixtures) and
    keep these plans as regression fixtures in backend/tests.
  - Until this is done, treat all output as a prototype.

Step 2 - Manual review and editing (biggest usability gain)
  - Let users correct room polygons, door positions and fixtures BEFORE
    electrical generation runs.
  - Then let users add, move and delete equipment on the canvas; the backend
    re-validates the change and regenerates circuits and BOQ.
  - Backend: PATCH endpoints for rooms/openings/points plus a "regenerate"
    call. Flutter: edit mode on ElectricalPlanCanvasScreen.

Step 3 - Make geometry trustworthy
  - Detect walls and room polygons with OpenCV first and let the AI only
    label them. Support non-rectangular rooms.
  - Validate the geometry (closed polygons, no overlaps, doors on walls,
    areas consistent with the scale) and refuse to generate when it fails.
  - Optionally read dimension text or scale bars to suggest a calibration.

Step 4 - Engineering depth
  - Voltage drop and cable-length checks per circuit; diversity and
    maximum-demand calculation for the main incomer.
  - Review the new equipment rules and prices with a licensed engineer and
    local suppliers (RWF pricing in the catalog is placeholder data).
  - Add BS 7671 and other standards through the existing base class, or hide
    them in settings until implemented.

Step 5 - Productise
  - Authentication and per-user projects; PostgreSQL via docker-compose.
  - PDF report export (currently an animated mock).
  - CI running pytest and flutter test; add .gitattributes; remove build
    artefacts, uploads and the zip from the repo; commit or discard the icon
    changes; merge the branch to main.
  - Remove mock_data usage from the Flutter app once the backend is the only
    data source.

Adding equipment (already easy):
  1. register_equipment(EquipmentSpec(...)) in backend/app/catalog/equipment.py
  2. To auto-propose it, add a rule in get_additional_equipment of
     engineering_rules/rs_iec_60364.py using catalog_point(...)
  3. Add the type to ElectricalPointType (lib/shared/models/electrical_point.dart)
     and a symbol in floor_plan_painter.dart.


7. RISKS TO KEEP IN MIND
------------------------
  - An electrical design is a safety document. The app proposes; a licensed
    engineer must review and approve. Keep the "needs confirmation" flags and
    the unverified-scale warnings visible to users.
  - Never reintroduce silent fallbacks: output that looks real but is not
    destroys trust faster than an explicit error.
  - Prices and quantities are estimates until validated locally.
